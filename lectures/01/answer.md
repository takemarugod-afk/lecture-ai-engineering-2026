- 考察：
  - **応答時間はほぼ「出力＋思考トークン数 ÷ 生成速度」で決まる。** 入力は7〜21トークンと小さく差がない。flash-lite は思考せず約190〜230 tok/s で、長文でも5秒以内。flash は「首都を一言で」でも約160トークン考えるため、1トークンの答えに約3秒かかる。長い質問では思考が約1,000トークン上乗せされ、TTFT が8〜9秒になる。gemma は約47 tok/s と遅く、思考もするので40秒前後かかった。
  - **このくらいの使い方では、無料枠の TPM はまず効かず、RPM と RPD が先に効く。** 1リクエストの入力は最大21トークンで、TPM 250K のごく一部。TPM は入力トークンだけを数えるので、思考や出力がいくら長くても TPM は減らない（AI Studio 上も入力トークン数での表示）。
  - **flash の RPD 20 は非常に少ない。** この計測だけで12回使った。第3回のエージェントのように1つの質問でツール呼び出しなど複数回 API を呼ぶと、数問で上限に届く。開発中は flash-lite（RPD 500）を使い、flash は確認用に絞るのが現実的。
  - **gemma は RPD 14.4K・RPM 30 と回数には余裕があるが、TPM が16Kと小さい。** 用語集や資料をプロンプトに入れて入力が長くなると（例：1回4,000トークンなら1分に4回まで）、回数より先に TPM で止まる。応答も遅いので、たくさん呼ぶ用途には向かない。
  - **429 と 503 は扱いを分ける必要がある。** AI Studio の消費量を見ると、flash-lite の RPD は同時送信の前後で10→27（＋17）で、429で断られた3件は数えられていなかった。一方 flash は503を含む3件を送って9→12になり、503で失敗したリクエストも RPD を消費していた。429 は `retry` の秒数だけ待てば安全に再試行できる。503 は再試行するたびに少ない RPD を減らすので、回数に上限を付ける必要がある。
  - **プログラムから連続で呼ぶときは「60 ÷ RPM」秒以上の間隔を空ける**（flash は12秒、flash-lite は4秒）。同時に投げると上限を超えやすい。
- 気づき・疑問：
  - 上限15なのに同時送信で17件通り、AI Studio のピークも「17 / 15」だった。上限ちょうどで厳密に止まるわけではないらしい。
  - `gemini-3.5-flash` で送ったリクエストが、AI Studio では「Gemini 3.6 Flash」の枠で数えられていた。モデル名が別名で、実体は新しいモデルなのかもしれない。
  - 計測は各条件2回程度と少なく、時間帯による混雑の影響も受ける（flash の503が多かった）。思考量は `thinking_config` で調整できるはずなので、思考を減らしたときの速度と回答品質の変化も確かめたい。
